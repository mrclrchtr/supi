## Workspace session deepening

### 1. Seam location
**Q:** Where should the deepened Workspace code-intelligence session seam live?

**A:** Internal to supi-code-intelligence ★
> Recommended: keep workflow policy with the code_* tools. supi-code-runtime stays the capability broker and canonical-type module.

### 2. Seam output
**Q:** What should cross the session seam back to code_* tool modules?

**A:** Typed immutable workflow outcomes ★
> Facts and explicit failure states only. Tool result assembly and markdown/TUI adapters remain outside. Callers cannot reach raw providers or mutate resolved targets.

### 3. Migration
**Q:** What must be true when this refactor lands?

**A:** All target-bearing tools use one path; replace, not layer ★
> Migrate code_resolve, code_graph, code_impact, code_orientation, and code_refactor_plan together. Remove `expandTargetId`, `executeResolveService`, and redundant target facades in the same landed change.

### 4. Target input
**Q:** What should enter the session seam?

**A:** Canonical Target workflow input; tool adapters normalize param names only ★
> Each tool maps its public parameters into the existing target-input vocabulary. The session owns targetId precedence, Scope behavior, file/coordinate pairing, and anchor requirements.

### 5. Workflow ownership
**Q:** How much behavior should sit behind the session seam?

**A:** All code_* analysis workflows ★
> The session coordinates target resolution, readiness, provider selection, and analysis for each intent. Internal modules still collect graph relations, inspection facts, etc. Tool modules retain public schema adaptation, Tool result assembly, and markdown/TUI adapters.

### 6. Failure contract
**Q:** How should expected failures cross the session seam?

**A:** Typed outcomes; tool adapter decides Pi failure ★
> Invalid input, disambiguation, timeout, unavailable capability, and partial evidence remain distinct typed outcomes. Internal defects may throw. The thin Pi adapter maps whole-workflow unavailable to a thrown tool failure.

### 7. Session state
**Q:** Where should non-tool Code intelligence session state live?

**A:** One session, behind intent-level behavior; fields become private ★
> The session owns target/plan handles, Instruction-File Surfacing deduplication, overview state, and coverage-warning timing. Lifecycle callers ask for outcomes rather than reading/mutating state.

### 8. Dependencies
**Q:** How should the session implementation obtain capabilities?

**A:** Inject one capability adapter at composition; no workflow reads globals ★
> The app composition root supplies the production adapter; session-interface tests supply the in-memory adapter. Internal workflow modules receive narrowed dependencies from the session implementation.

### 9. Test surface
**Q:** What should become the authoritative test surface?

**A:** Session interface tests + focused algorithm tests; delete forwarding tests ★
> Add behavior tests for every workflow intent, precedence rule, failure state, and partial result through the session interface. Keep focused algorithm tests. Delete forwarding and compatibility-path tests.

### 10. Concurrency
**Q:** What concurrency policy should the deepened session enforce?

**A:** Concurrent workflows; targeted file-mutation queues only ★
> Read-only workflows run concurrently. Small in-memory target/plan updates remain atomic. File mutation keeps the existing sorted per-file queue.

### 11. Implementation shape
**Q:** How should the deepened session implementation be organized?

**A:** Cohesive facade over private domain modules ★
> WorkspaceCodeIntelligenceSession remains the external seam. Target workflow, graph collection, impact, search, health, refactor, and session state stay as private implementation modules grouped by domain.

### 12. Interface shape
**Q:** How should callers select a workflow at the session seam?

**A:** One typed entry per code_* intent ★
> Each entry accepts canonical domain input plus per-call abort/progress controls. Nine entries mirror nine genuine behaviors without exposing schemas, providers, or internal modules.

### 13. Compatibility
**Q:** Should this refactor remove the unused capability/context surfaces it supersedes?

**A:** Hard cut: remove `createWorkspaceContext`, `buildAnalysisContext`, `getCodeProvider`, `expandTargetId`, `executeResolveService`, stale re-exports ★
> Delete unused exports and tests that only prove forwarding. SuPi is pre-release and permits intentional breaking changes.

### 14. Execution controls
**Q:** How should cancellation and progress cross the session seam?

**A:** Per-call AbortSignal and domain progress events ★
> Each workflow receives an AbortSignal and optional progress sink for stable phase events. Internal subprocess/provider calls receive the signal. The thin Pi adapter translates phase events into onUpdate text.

### 15. Partial evidence
**Q:** What should the session return for a mixed graph request (references + callees) when the target has only a Declaration anchor?

**A:** References succeed; callees explicitly unavailable ★
> Resolve the target once, collect position-tolerant evidence, and return a typed unavailable section for the strict relation. Tool result assembly discloses the partial result.

### 16. Impact modes
**Q:** How should the session handle target input mixed with a Change set?

**A:** Reject mixed impact modes ★
> Return typed invalid input and tell the caller to choose a Resolved target or a Change set. No target or file input is silently ignored.

### 17. Validation
**Q:** Where should cross-field and semantic validation live after the migration?

**A:** Session owns canonical validation ★
> Tool adapters rely on Pi for structural schema validation and only map parameter names. The session validates pairing, exclusivity, Scope existence, target precedence, operation requirements, and capability preconditions.

### 18. Integration tests
**Q:** How much real-substrate verification should the session interface receive?

**A:** Small semantic + structural contract matrix ★
> Keep exhaustive policy tests on in-memory adapters, then add a focused session-interface matrix using the real TypeScript LSP and Tree-sitter: anchored resolution, symbol disambiguation, mixed graph evidence, stale handle, refactor planning.

## Public tool redesign

### 26. Tool surface
**Q:** How much may the public code_* tool interface change in this migration?

**A:** Redesign tool schemas too *(against recommendation)*
> Recommendation was to preserve names, schemas, and evidence semantics. User chose to reshape the public interface.

### 27. Primary goal
**Q:** What should the code_* tool redesign optimize first?

**A:** Schema coherence across focused intents ★
> Keep orientation, graph, find, health, inspect, resolve, plan, and apply as distinct tools, but derive their target/scope/result contracts from one coherent vocabulary.

### 28. Target schemas
**Q:** Which schema family should anchor the redesigned code_* interface?

**A:** Nested, discriminated target values ★
> Target-oriented tools receive one `target` value with explicit variants (handle, anchor, symbol, file). code_inspect keeps a `point` value. code_orientation keeps `focus`. Invalid mixtures are structurally impossible.

### 29. Resolve workflow
**Q:** Should focused analysis tools accept direct target variants as well as handles?

**A:** Yes, with intent-specific allowed variants ★
> Graph and impact accept handle, anchored, or symbol-query variants. Refactor planning accepts handle or anchored variants. Symbol-centered orientation accepts the same target value. The session applies one Target workflow regardless of entry tool.

### 30. Target vocabulary
**Q:** How should target variants identify themselves?

**A:** `type` with explicit variants: `handle`, `anchor`, `symbol`, `file` ★
> Examples: `{ type: "handle", id }`, `{ type: "anchor", file, line, character }`, `{ type: "symbol", query, scope?, symbolKind? }`, `{ type: "file", file }`. Search `kind` remains AST-specific.

### 31. Impact evidence
**Q:** What role should a proposed-change description have?

**A:** **Needs discussion** *(unanswered)*
> User comment: "let's remove brittle tools/functionalities"

### 32. Deletion rule
**Q:** What should qualify a tool or mode for removal?

**A:** Any heuristic or convention-based result *(against recommendation)*
> Recommendation was evidence-based ("no reliable substrate contract or integration test"). User chose the stricter evidence-purity criterion.

### 33. Heuristic scope
**Q:** Should the no-heuristics rule apply only to Tool evidence, or to every emitted hint?

**A:** Tool evidence only ★
> Remove heuristic and convention-based facts, counts, risk claims, affected sets, and test associations. Read-next guidance and suggested follow-up commands may remain when clearly separated and never counted as evidence.

### 34. code_impact
**Q:** What should happen to code_impact under the no-heuristics rule?

**A:** Remove code_impact entirely ★
> Use code_graph references/implementations for provider-backed relationships. A user-supplied Change set remains caller context, not an inferred blast-radius report.

## Continued grilling

### 35. Evidence-locator cutoff
**Q:** Where should the no-conventions cutoff sit for Tool evidence?

**A:** Locator-only rule ★
> A deterministic convention may locate an artifact, but it may not create a classification, relationship, or claim in Tool evidence. Located facts retain provenance; absence at one location is not proof of global absence.

### 36. Test relations
**Q:** Should `code_graph.tests` survive the evidence-locator rule?

**A:** Remove it without replacement ★
> The current relation mixes semantic references with filename and package-layout conventions. Direct structural test search through `code_find` may remain; a graph relation can return only if a provider-backed relationship earns the seam later.

### 37. File inventories in `code_graph`
**Q:** Should `imports` and `exports` remain graph relations?

**A:** Remove both ★
> They are file-level syntax inventories rather than resolved graph edges. Direct structural access remains through `code_find` and file orientation; genuine dependency edges can return only if a provider-backed relationship later earns the seam.

### 38. First-turn overview
**Q:** Should the hidden first-turn Code Intelligence Overview remain automatic?

**A:** Keep the current overview *(against recommendation)*
> The overview continues to scan workspace metadata and inject a hidden, bounded architecture summary once per branch. The recommendation was to remove automatic injection in favor of on-demand Orientation for stronger Context Efficiency.

### 39. Surviving public tool family
**Q:** Should the public family be the proposed eight tools: `code_resolve`, `code_inspect`, `code_orientation`, `code_graph`, `code_find`, `code_health`, `code_refactor_plan`, and `code_refactor_apply`?

**A:** Yes ★
> Remove `code_impact`, the legacy `rename` refactor-operation alias, and the `tests`, `imports`, and `exports` graph relations. `code_graph` keeps `references`, `callees`, `implements`, and a coherent `all`.

### 40. Target interface design
**Q:** Which concrete target representation should anchor the redesigned public tool interface after comparing four alternatives?

**A:** Single-key exact-one selector ★
> Use intent-specific selectors such as `{ target: { handle: "..." } }`, `{ target: { anchor: { file, line, character } } }`, `{ target: { symbol: { query, scope?, symbolKind? } } }`, and `{ target: { file: "..." } }`. Enforce exactly one branch with `minProperties: 1`, `maxProperties: 1`, and `additionalProperties: false`, avoiding `Type.Union`/`Type.Literal`. This supersedes the earlier `type`-field syntax while preserving explicit variants and structural exclusivity.

### 41. Orientation focus interface
**Q:** How should `code_orientation` represent non-workspace focus with the exact-one selector design?

**A:** Exact-one focus with nested target ★
> Omitted `focus` means workspace orientation. Otherwise accept exactly one of `{ focus: { path } }`, `{ focus: { module } }`, or `{ focus: { target: TargetSelector } }`. The nested target permits handle, anchor, or symbol selectors; direct file orientation uses the path branch. This preserves Orientation focus as distinct from a Resolved target.

### 42. Refactor operation interface
**Q:** How should `code_refactor_plan` represent operation-specific inputs after removing the legacy `rename` alias?

**A:** Exact-one operation selector ★
> Use `operation: { rename_symbol: { newName } }`, `operation: { extract_function: { newName, range } }`, or `operation: { extract_variable: { newName, range } }`. Structural schemas require operation-specific fields and reject extras; the session still validates range ordering, target suitability, readiness, and provider precision.

### 43. ADR structure
**Q:** How should the combined migration be recorded before implementation?

**A:** Three new ADRs plus surgical updates ★
> Add ADR 0015 for the deep Workspace code-intelligence session and Tool result assembly, superseding ADR 0008; ADR 0016 for Workspace LSP runtime ownership; and ADR 0017 for the eight-tool interface, exact-one selectors, locator-only evidence rule, and removals. Surgically align ADRs 0002, 0004, 0005, and 0007 plus `docs/tool-architecture.md`, preserving their surviving decisions and adding cross-references.

### 44. Legacy target precedence
**Q:** What should happen to old flat target calls and their `targetId` precedence after adopting structurally exclusive selectors?

**A:** Hard cut; retire precedence ★
> Accept only the new exact-one interface. Do not add `prepareArguments` normalization or dual internal shapes. New calls cannot mix target variants, stale handles never fall back, and resumed sessions containing old argument shapes may fail validation.

**A:** Confirmed — implement ★
