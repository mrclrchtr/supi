# Contributing to SuPi

Report bugs and propose features as [GitHub issues](https://github.com/mrclrchtr/supi/issues). After a task with SuPi tools, `/supi-tooling-retro` from `supi-debug` drafts useful feedback.

## Set up a checkout

Requires [mise](https://mise.jdx.dev). It provides the pinned Node.js, pnpm, hk, and Pkl versions from `.mise.toml`.

```sh
git clone https://github.com/mrclrchtr/supi.git
cd supi
mise install
pnpm install
mise run hooks
```

`mise run hooks` runs `hk install --mise` and writes the Git hooks into this clone's `.git/config`. Installing them is a trust decision: the hooks run commands from `hk.pkl` on every commit, checkout, merge, and rebase.

## Git hooks

| Hook | Runs |
| --- | --- |
| `pre-commit` | Merge-conflict markers, gitleaks on staged content, large files, Biome, and trailing whitespace. Fixes are applied with `stash = "none"`, so unstaged changes in fixed files can be staged too. |
| `commit-msg` | commitlint ([Conventional Commits](https://www.conventionalcommits.org)) |
| `post-checkout` (branch switches), `post-merge` (including `git pull`), `post-rewrite` (rebases) | `pnpm install --frozen-lockfile`, so `node_modules` follows `pnpm-lock.yaml` |

Run the pre-commit fixes without committing with `hk fix`. Skip all hooks once with `HK=0`.

## Run SuPi from the working tree

Pi loads the extensions directly from source; there is no build step. `.pi/settings.json` declares the repository root as a package, so opening Pi in this directory loads every extension listed in `package.json#pi.extensions`.

1. Start `pi` in the repository root and grant project trust with `/trust`.
2. After editing extension code, run `/reload` or restart Pi.

## Checks

| Command | Covers | Use when |
| --- | --- | --- |
| `pnpm check:fast` | Biome | Quick feedback while editing |
| `pnpm check` | Biome, TypeScript, skills catalog, and unit tests | Before pushing a change |
| `pnpm test:servers` | Tests against real language servers | You changed `supi-lsp` or the LSP substrate of Code Intelligence |
| `pnpm verify` | `check`, language-server tests, WASM grammars, and package tarballs | Dependency, packaging, or cross-package changes |
| `pnpm check:fix` | Biome fixes | Formatting or lint failures |

Language-server tests need the matching servers on `PATH`. Scripts ending in `:ai` produce lower-noise output for coding agents. CI runs the gates in [CI and release gates](docs/conventions/ci-verification.md) on every PR and every push to `main`.

## Commits and versioning

- Development is trunk-based: `main` is the only long-lived branch and stays releasable. Maintainers land work on `main` without a pull request. Outside contributions arrive as pull requests and are rebase-merged, so every commit of a PR lands unchanged.
- Write commit messages as Conventional Commits; the `commit-msg` hook and CI enforce them.
- All published packages share one semver version. Breaking changes need a `BREAKING CHANGE` commit footer and a migration step in the affected package changelog ([package changelogs](docs/conventions/package-changelogs.md)).
- Maintainers release with `pnpm release:prepare` ([release preparation](docs/conventions/release-preparation.md)). Do not edit versions by hand.

## Repository layout

- `packages/` — one directory per package. Follow the [package layout](docs/conventions/package-layout.md) and, for tool packages, the [tool architecture](docs/conventions/tool-architecture.md).
- `docs/` — reference docs for extension development; start at [docs/INDEX.md](docs/INDEX.md).
- `skills/` — the public skills catalog, generated by the private [`supi-skill-patches`](packages/supi-skill-patches/README.md) workspace. Change skills through its [maintenance workflow](packages/supi-skill-patches/README.md#maintenance), not in `skills/` directly.
- [`supi-test-utils`](packages/supi-test-utils/README.md) — private test helpers such as `createPiMock()` and `makeCtx()`. Follow the [testing convention](docs/conventions/testing.md) when you add or change tests.

`CLAUDE.md` collects repository rules and gotchas for coding agents; they apply to human contributors as well.
