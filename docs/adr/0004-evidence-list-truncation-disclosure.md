# Evidence lists disclose truncation for public tool evidence

**Context.** `supi-code-intelligence` public tools cap many result sections for readability, but capped markdown and structured details can drift or silently imply completeness. Silent truncation violates honest correctness: a user or agent must distinguish “there are no more results” from “more evidence exists but was not shown.”

**Decision.** Public Tool evidence and generated executable/check commands use bounded evidence/actionable lists with shared completeness metadata. `ToolResultAssembly` is the canonical interface for sections, lists, totals, omission metadata, confidence, provenance, and follow-up actions.

Normal public-tool paths compute exact totals; `maxResults` is a display cap, not a collection cap. Each capped list discloses truncation in markdown with `_(showing X of Y; N omitted)_`, and structured details carry matching metadata under stable dotted keys such as `references.locations`, `health.diagnostics`, `inspect.codeActions`, or `refactor.edits`.

Counts use evidence atoms, not rendered grouping rows: reference locations count as references even when grouped by file, and individual diagnostics count as diagnostics even when grouped by file. Unknown totals are allowed only for exceptional interruption or provider-limited results and must carry an explicit partial reason. A partial list keeps `totalCount: null`, while `omittedCount` records only known collected Evidence atoms hidden by the display cap; it never counts files or potential evidence that the incomplete operation did not inspect. When a provider returns locations that cannot be normalized, valid normalized evidence keeps exact shown/total/omitted counts while `invalidLocationCount` and the `invalid-provider-location` partial reason disclose the rejected provider atoms separately; invalid locations are neither project nor external evidence. Evidence-list policy remains internal to `supi-code-intelligence` until another package has a concrete need for it.

**Considered Options (rejected).** Renderer-only notes were rejected because markdown and structured details would drift. Details-only metadata was rejected because human-readable output could still look complete. Per-tool custom truncation logic was rejected because it would encode the same invariant differently across tools. Treating `maxResults` as a collection cap was rejected because it prevents exact omission counts on normal paths. Promoting evidence lists to `supi-code-runtime` was rejected as premature generalization.

**Consequences.** The invariant applies to Orientation facts, graph relations, search results, resolve candidates, health evidence, inspect facts, refactor edit previews, and generated verification commands. Prose guidance such as `nextQueries` remains guidance chrome. Markdown and TUI adapters consume assembled completeness data instead of recomputing it. Tests assert both rendered disclosure and matching structured metadata. Grouped reference rendering caps reference locations, not file groups.
